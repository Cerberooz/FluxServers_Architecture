You are working on the **FluxServers hosting panel**.

Your task is to inspect the existing codebase and prepare the panel for a network infrastructure change affecting how Minecraft server connection addresses and customer subdomains are managed.

## New infrastructure

FluxServers will use this architecture:

```text
Customer
   ↓
play.fluxservers.cloud:<allocated-port>
   ↓
Sucura Networks protected IP
   ↓
HatchHost Minecraft node:<same-port>
   ↓
Customer Minecraft server
```

There will initially be:

* One HatchHost Minecraft hosting node, currently planned as a 48 GB node.
* One Sucura Networks Minecraft protection endpoint.
* Sucura provides one protected frontend IP / DNS record and one backend node.
* Two small VPS instances remain responsible for web, panel, database, and other supporting operations.

The important design change is that **customers should never need the HatchHost node's real public IP as their displayed server address.**

The canonical protected hostname will be:

```text
play.fluxservers.cloud
```

It will resolve to the Sucura protected IP.

Each Minecraft server receives its own allocated port from the hosting node.

Example:

```text
Customer server allocation:
HatchHostNodeIP:3333
```

The customer-facing default address should instead be:

```text
play.fluxservers.cloud:3333
```

Sucura is expected to forward the connection to:

```text
HatchHostNodeIP:3333
```

Do **not** hardcode the HatchHost IP, Sucura IP, or ports into application logic.

# Customer custom subdomains

FluxServers already supports or is intended to support customer-managed subdomains.

For example, a customer allocated port:

```text
3333
```

may choose:

```text
james.fluxservers.cloud
```

The system should NOT create:

```dns
james.fluxservers.cloud A <Sucura IP>
```

unless the existing DNS implementation requires an A/CNAME record for some unrelated reason.

Instead, Minecraft custom domains should use an **SRV record**:

```dns
_minecraft._tcp.james.fluxservers.cloud
```

with:

```text
Priority: 0
Weight: 0
Port: 3333
Target: play.fluxservers.cloud
```

Conceptually:

```text
james.fluxservers.cloud
        ↓ Minecraft SRV lookup
play.fluxservers.cloud:3333
        ↓
Sucura protected IP:3333
        ↓
HatchHost node:3333
```

This means **no wildcard ****`*.fluxservers.cloud`**** A record is required for Minecraft customer subdomains.**

# Server node migration

This is separate from simply being "multi-node ready."

```dns
_minecraft._tcp.james.fluxservers.cloud
SRV 0 0 4217 play.fluxservers.cloud.
```

## Migration synchronization

When a server successfully moves to another node, immediately synchronize all dependent state.

At minimum verify/update:

* server node association
* Pterodactyl server ID/reference
* allocation ID
* allocation port
* any internally stored allocation IP if required
* customer-facing public address
* custom subdomain association
* DNS SRV record
* DNS provider record ID
* server ownership / user associations if the existing schema requires them
* any cached server/allocation information

Do not change user ownership simply because a server changes nodes.

Instead, ensure all existing server-to-user relationships remain intact and that no migration workflow accidentally leaves stale node-specific user/server references.

The database should have one clear source of truth for:

```text
server
→ node
→ allocation
→ customer
→ custom subdomain
```

Avoid duplicating this relationship unnecessarily.

# Immediate DNS synchronization after migration

Do not rely on the reconciliation job for normal server moves.

DNS should be updated as part of the normal migration workflow as soon as the destination allocation is known and the server move has successfully reached the appropriate state.

Conceptually:

```text
Move requested
      ↓
Destination node selected
      ↓
Pterodactyl migration
      ↓
Destination allocation confirmed
      ↓
Persist new node/allocation
      ↓
Synchronize SRV record immediately
      ↓
Refresh derived public address
      ↓
Migration complete
```

If the server has no custom subdomain, no SRV record needs to be changed.

If it does have one, update its SRV port to the new allocation port.

Use an idempotent synchronization method, conceptually:

```text
syncMinecraftDnsForServer(serverId)
```

The same synchronization method should be reusable by:

* subdomain creation
* subdomain updates
* allocation changes
* server node migrations
* administrator repair actions
* reconciliation jobs

Do not implement separate slightly-different DNS update logic for each workflow.

# DNS reconciliation job

Implement a scheduled reconciliation job that runs **once every hour**.

Its purpose is to detect and repair drift between:

```text
FluxServers database
Pterodactyl state
DNS provider state
```

This is a safety mechanism.

It should NOT replace immediate synchronization during normal operations.

The architecture should therefore be:

```text
Normal change
    ↓
Immediate synchronization

PLUS

Every hour
    ↓
Reconciliation / repair
```

## Source of truth

Determine which existing system should be authoritative for each field.

Unless the current architecture requires otherwise, prefer:

```text

- actual server node

- actual allocation port

```

Do not blindly make DNS the source of truth.

# Hourly reconciliation algorithm

For every active Minecraft server:

1. Retrieve its current expected Pterodactyl server/node/allocation state.

2. Compare it against the FluxServers database.

3. Repair stale FluxServers node/allocation information where appropriate.

4. Determine the expected customer-facing address:

```text
MINECRAFT_PUBLIC_HOST:<actual-primary-allocation-port>
```

5. If there is no custom subdomain:

   * ensure no stale managed SRV record exists for a previously removed subdomain where this can be safely determined.

6. If there is a custom subdomain, calculate the expected SRV record:

```text
_minecraft._tcp.<subdomain>.fluxservers.cloud
```

with:

```text
priority = 0
weight = 0
port = actual allocation port
target = MINECRAFT_PUBLIC_HOST
```

7. Retrieve or otherwise inspect the corresponding DNS provider record.

8. Compare actual DNS state against expected state.

9. If the record is missing:

   * recreate it.

10. If its target, port, name, priority, or weight is incorrect:

    * update it.

11. If the database contains an invalid/stale DNS record ID:

    * locate the correct managed record if safely possible.
    * repair the stored record ID.

12. Record the reconciliation result.

The operation should be idempotent.

Running reconciliation multiple times against already-correct state must result in no unnecessary DNS writes.

* expected `_minecraft._tcp.<customer-subdomain>` names
* the configured FluxServers DNS zone

Never modify unrelated DNS records in the zone.

# Migration failure handling

Node migrations are multi-step operations and can partially fail.

Do not update DNS to the destination port before the destination allocation is authoritative.

Likewise, do not leave DNS permanently pointing at an old port after a successful migration.

Structure migration state changes carefully.

Conceptually:

```text
Pterodactyl migration succeeds
        ↓
destination allocation confirmed
        ↓
Flux database updated
        ↓
DNS synchronization attempted
```

If DNS synchronization fails after the server migration itself succeeded:

* do not incorrectly revert the server's node/allocation database state
* record the DNS synchronization failure
* retry using the project's existing retry mechanism if appropriate
* allow the hourly reconciliation job to repair the DNS record later

This distinction is important:

```text
server migration state
```

and:

```text
DNS synchronization state
```

must not be treated as one atomic external transaction because Pterodactyl and the DNS provider are independent systems.
